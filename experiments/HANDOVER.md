# Handover: Custom Offline-First Spaced Repetition System (GitHub Notes)

## 1. Project Purpose & History

The user keeps daily learning notes in a GitHub repository and requires a system to review them using a strict, fixed-step spaced repetition algorithm: **1, 3, 5, 7, 14, and 60 days**.

Initially, this was going to be built as an Anki add-on. However, Anki's native scheduler penalizes late reviews, and custom Python add-ons only work on desktop, breaking the user's requirement to review on mobile devices.

To achieve true **"no-lapse"** behavior across all devices with zero compromises, the project has pivoted to a **Custom Offline-First Flutter Application** backed by **Firebase** and **GitHub Actions**.

### The "No-Lapse" Core Rule
This is the most critical requirement of the system:
- A review only advances to the next step when the user explicitly marks it **"Revised"**.
- If a user reviews a card 10 days after it was due, nothing is penalized, nothing duplicates, and the next interval is computed from the **actual day they revised**, NOT the original due date.
  - *Example:* On the 5-day step, if reviewed 10 days late, the next step (7 days) counts from today.
- Once the 60-day step is completed, the note is marked **"mastered"** and permanently exits the active rotation.

## 2. Architecture Overview

The system is fully decoupled into three components. It relies on local SQLite/Drift databases for instant offline UI updates, with Firebase handling background synchronization.

### Component A: Content Generator (GitHub Actions / Python)
- **Trigger:** Daily cron job running on the GitHub repository.
- **Action:** Runs a Python script using GitPython to walk the commit history. It groups commits by calendar day.
- **Parsing:** Extracts raw patch diffs (Git hunks), ignoring deletions, and formats the additions alongside a few lines of unchanged context for readability.
- **Output:** Generates a single `daily_notes.json` file and commits it back to the repository. This acts as a free, read-only CDN.

### Component B: Backend & Auth (Firebase)
- **Auth:** Firebase Authentication (Email/Password or GitHub OAuth) to allow cross-device usage.
- **Database (Firestore):** A lightweight NoSQL store that only holds the scheduling state, not the heavy note content. Guarantees zero cold starts.

### Component C: Frontend Client (Flutter PWA / Native App)
- **Environment:** Developed in Visual Studio Code, using Android Studio for emulation and native builds.
- **Data Strategy (Offline-First):**
  1. Downloads `daily_notes.json` from GitHub.
  2. Downloads the user's progress from Firestore.
  3. Merges both into a local Drift (SQLite) database.
- **UI/UX:** Presents a queue of due notes. The user only has one action button: **"Mark Revised"**. Pressing this immediately updates the Drift database (computing the next due date based on today) and updates the UI instantly. A background sync engine then pushes this new date to Firestore.

## 3. Data Models

### 3.1 GitHub JSON Output (`daily_notes.json`)
Generated by Component A.

```json
[
  {
    "guid": "a1b2c3d4e5f6g7h",
    "date": "2026-08-15",
    "files": [
      {
        "filename": "flutter_architecture.md",
        "hunks": [
          {
            "heading": "## Drift Setup",
            "lines": [
              {
                "type": "context",
                "text": "  import 'package:drift/drift.dart';"
              },
              {
                "type": "add",
                "text": "+ @DataClassName('Note')"
              }
            ]
          }
        ]
      }
    ]
  }
]
```

### 3.2 Firestore Sync Document (`user_progress`)
Stored in Component B.

```json
{
  "user_id": "firebase_auth_uid",
  "note_guid": "a1b2c3d4e5f6g7h",
  "current_step": 2, // Maps to the 5-day interval
  "next_due_date": "2026-08-20T00:00:00Z",
  "is_mastered": false
}
```

### 3.3 Local Drift Database (SQLite)
The Flutter app will join the data from GitHub and Firebase into a unified local table for querying.

| Column | Type | Constraints / Default |
|---|---|---|
| `guid` | String | Primary Key |
| `date_created` | String | Date note was generated |
| `content_json` | String / Text | Serialized file hunks |
| `current_step` | Integer | Default `0` |
| `next_due_date` | DateTime | Default to tomorrow upon initialization |
| `is_mastered` | Boolean | Default `false` |

## 4. Phased Implementation Plan

### Phase 1: Component A (Python Script & Actions)
- Write the Python script using GistPython to extract hunks and output the `daily_notes.json` structure shown above.
- Set up the GitHub Actions YAML to run this daily and commit the JSON back to the repository.

### Phase 2: Component B (Firebase Initialization)
- Provide instructions to initialize a Firebase project, enable Authentication, and set up a Firestore database with basic security rules (users can only read/write their own `user_id` documents).

### Phase 3: Component C - Part 1 (Flutter Core & Local DB)
- Initialize the Flutter project.
- Set up Drift (SQLite) to handle the local data models.
- Build the data-fetching service: fetch `daily_notes.json` via standard HTTP GET and parse it into the Drift database.
- Implement the UI: A simple daily queue displaying notes where `next_due_date <= today` and `is_mastered == false`. Include syntax highlighting for the Git hunks.

### Phase 4: Component C - Part 2 (Scheduling Logic & Sync)
- Implement the "Mark Revised" logic strictly following the interval array: `[1, 3, 5, 7, 14, 60]`. Ensure the calculation is always `DateTime.now().add(Duration(days: interval))`.
- Wire up the Firebase SDK. Ensure that when Drift updates locally, the change is pushed to Firestore. When the app boots, fetch from Firestore to update Drift.
- Deploy as a Progressive Web App (PWA) via GitHub Pages or Firebase Hosting for immediate mobile testing.
